# BC카드 상권위험 진단·Neo4j GraphRAG 구현 및 검증 정리

기준일: 2026-09-13  
BC 데이터 기간: 2026-01~06  
분석 단위: 월×시군구×업종

## 1. 프로젝트 목적

BC카드 소비 데이터와 외부 상권 데이터를 이용해 다음 서비스를 구현하는 것이 목적이다.

1. 지역×업종에서 나타나는 여러 위험을 모델이 동시에 진단한다.
2. Neo4j에서 해당 지역의 과거 흐름, 유사 상권, 과거·최근 트렌드와 실제 마케팅 사례를 검색한다.
3. LLM이 사업자에게 추가 질문을 하고 상권 문제와 점포 내부 문제를 구분한다.
4. 확인된 상황에 맞는 소규모 개선 실험과 검증 KPI를 제안한다.
5. 향후 개선안 실행 결과가 축적되면 Collaborative Filtering 추천으로 확장한다.

이 모델은 개별 점포의 폐업 여부를 예측하지 않는다. BC 원본이 점포 단위가 아니므로 출력은 **지역×업종의 위험 신호**다.

## 2. 전체 구조

```text
BC 소비 + 외부 상권 데이터
            ↓
월×시군구×업종 특징 생성
            ↓
멀티라벨 위험확률 예측
 ├─ 수요 위축
 ├─ 객단가 압력
 ├─ 고객구조 편중
 └─ 경쟁 압력
            ↓
Neo4j GraphRAG
 ├─ 해당 상권 과거 점포동학
 ├─ 과거 BC 관측
 ├─ 유사 위험 상권
 ├─ 과거·최근 트렌드
 └─ 실제 마케팅 사례
            ↓
사업자 추가 질문 최대 3개
            ↓
LLM 조건부 해석·개선 실험·KPI
            ↓
사업자×개선안×성과 피드백 적재
            ↓
향후 Collaborative Filtering
```

- 원본 행 수: 242,574행

- 제한: 점포 식별자, 개별 점포 매출, 폐업 여부가 없음

### 외부데이터

- LOCALDATA 점포 인허가일·폐업일·시설면적·좌표
- 정확 업종 월별 공급 패널
- 주민등록 연령인구
- CPI
- 등록외국인
- 기상
- 상업용부동산 임대·공실

## 4. 라벨 설계

현재 월 `t`의 소비·고객구조·공급 특징으로 다음 월 `t+1` 결과를 예측한다. 현재 지표로 현재 규칙을 그대로 재현하는 순환 모델을 피하기 위한 시간 분리다.

| 라벨 | 정의 |
|---|---|
| 수요 위축 | 다음 달 CNT와 AMT 증가율이 동일 월·동일 업종에서 모두 하위 25% |
| 객단가 압력 | 다음 달 건당금액 증가율이 동일 월·동일 업종 하위 25% |
| 고객구조 편중 | 다음 달 고객 세그먼트 HHI 증가가 동일 월·동일 업종 상위 25% |
| 경쟁 압력 | 다음 달 공급수준 상위 25%이면서 점포당 AMT 대리값 증가율 하위 25% |
| 복합 위험 | 네 위험 중 모델 확률 0.5 이상이 두 개 이상 |

경쟁 압력은 공급 데이터가 정확히 연결되는 편의점·슈퍼마켓·제과점·중국음식 범위에서만 산출한다. 다른 업종은 0이 아니라 결측으로 둔다.

## 5. 멀티라벨이 필요한 이유

2026년 6월 홀드아웃 2,344개 지역×업종에서 공통 세 위험을 확인했다.

| 위험 개수 | 지역×업종 수 |
|---:|---:|
| 0개 | 1,102 |
| 1개 | 898 |
| 2개 | 307 |
| 3개 | 37 |

둘 이상의 위험이 동시에 발생한 행은 344개, 14.7%다. 따라서 수요 위축과 객단가 압력처럼 함께 나타나는 문제를 하나의 클래스로 강제하면 정보가 손실된다.

복수위험 행에서 하나의 문제만 출력하는 모델은 정답 라벨 전체 중 이론적으로 최대 47.4%만 회수할 수 있다.

### 동일 홀드아웃 비교

| 모델 | Micro-F1 | Macro-F1 | 복수위험 Recall |
|---|---:|---:|---:|
| 한 문제 강제 Logistic | 0.234 | 0.191 | 0.290 |
| Binary Relevance Logistic | 0.361 | 0.349 | **0.622** |
| Classifier Chain Logistic | 0.358 | 0.346 | 0.615 |
| Binary Relevance Random Forest | **0.390** | **0.371** | 0.563 |

멀티라벨의 타당성은 성능 차이만이 아니라 **정답이 실제로 동시 발생한다는 구조**에서 나온다. 모델 비교는 그 구조를 보조적으로 확인한다.

Subset Accuracy와 Hamming Loss는 양성 라벨이 적을 때 아무 문제도 출력하지 않는 보수적 모델에 유리할 수 있으므로 Micro/Macro-F1, 라벨별 Average Precision, 복수위험 Recall을 함께 사용한다.

## 6. 현재 위험 모델 결과

학습은 4,676행, 평가는 2026년 6월 2,344행으로 시간 분리했다.

| 위험 | ROC-AUC | Average Precision | 해석 |
|---|---:|---:|---|
| 수요 위축 | 0.553 | 0.220 | 현재 특징만으로 신호가 약함 |
| 객단가 압력 | 0.614 | 0.389 | 제한적인 구분 신호 |
| 고객구조 편중 | 0.528 | 0.257 | 거의 기준선 수준 |
| 경쟁 압력 | 0.833 | 0.093 | 양성 29/1,010으로 심한 불균형; AUC 단독 해석 금지 |

현재 성능은 배포 가능한 모델을 뜻하지 않는다. 6개월 자료로 `t→t+1` 학습 구조와 서비스 파이프라인이 작동함을 보여주는 기준선이다.

## 8. Neo4j 데이터 모델

```text
(:Region)<-[:OBSERVED_IN]-(:Observation)-[:FOR_INDUSTRY]->(:Industry)
(:Region)<-[:OBSERVED_IN]-(:MarketHistory)-[:FOR_INDUSTRY]->(:Industry)
(:Case)-[:ADDRESSES]->(:Problem)
(:Case)-[:EVIDENCES]->(:Trend)
(:Business)-[:LOCATED_IN]->(:Region)
(:Business)-[:IN_INDUSTRY]->(:Industry)
(:Business)-[:TRIED]->(:Intervention)-[:RESULTED_IN]->(:Outcome)
```

### 주요 노드

- `Region`: 시도·시군구
- `Industry`: BC 업종
- `Observation`: BC 월별 소비·고객구조 관측
- `MarketHistory`: 월별 점포·개업·폐업·회전률
- `Problem`: 네 가지 위험
- `Trend`: 시대별 마케팅 트렌드
- `Case`: 기업 공식 실행 사례
- `Business`: 익명화된 서비스 사용자
- `Intervention`: 실제 선택한 개선안
- `Outcome`: 비교집단 대비 CNT·AMT·마진·재방문 증분

운영 API는 `REQUIRE_NEO4J=true`일 때 접속정보가 없으면 실행을 거부한다. 노트북 개발 환경에만 CSV fallback을 허용한다.

## 9. GraphRAG 검색 순서

1. 모델의 위험확률 상위 항목을 확인한다.
2. Neo4j에서 동일 지역×업종의 과거 BC 관측을 조회한다.
3. 2019년 이후 개업·폐업·순점포 경로를 조회한다.
4. 위험 프로필이 유사한 다른 지역을 찾는다.
5. 해당 문제와 연결된 시대별 트렌드와 실제 사례를 검색한다.
6. 검색 근거, 출처 URL, 주의사항을 LLM 입력에 함께 전달한다.
7. LLM은 확인된 사실·가능한 설명·추가 질문·조건부 실험을 분리한다.

LLM이 자체 기억만으로 마케팅 사례를 만들지 않고 그래프가 반환한 근거를 먼저 사용하도록 구성했다.

## 10. 사업자 추가 질문

위험확률이 높은 순서대로 최대 세 질문만 제시한다.

- 수요 위축: 영업일당 주문건수와 재방문 고객이 실제로 줄었는가?
- 객단가 압력: 가격·할인·세트 변경 후 주문당 마진이 변했는가?
- 고객 편중: 특정 연령·시간대 외 고객의 방문이 줄었는가?
- 경쟁 압력: 500m 내 신규점과 배달·가격·메뉴가 얼마나 겹치는가?

점포 답변이 없으면 지역 수준의 가능성만 제시하고 직접 원인을 단정하지 않는다.

## 11. LLM 출력

OpenAI Responses API를 호출하며 다음 JSON 구조를 요구한다.

```json
{
  "summary": "상권 진단 요약",
  "observed_signals": ["데이터에서 확인된 사실"],
  "questions": ["사업자 확인 질문"],
  "recommended_experiments": ["조건부 소규모 실험"],
  "kpis": ["CNT·AMT·마진·재방문 등"],
  "cautions": ["해석 제한"]
}
```

`OPENAI_API_KEY`가 없으면 호출하지 않고 `LLM_NOT_CALLED`를 반환한다. 키는 코드·노트북·Git에 저장하지 않는다.

## 12. Collaborative Filtering 적용 조건

과거 상권 데이터만으로는 Collaborative Filtering이 성립하지 않는다. CF에는 사용자와 아이템 간 상호작용이 필요하다.

필요 로그는 다음과 같다.

| 필드 | 내용 |
|---|---|
| `business_id` | 익명 사업자 ID |
| `intervention_id` | 제안·선택한 개선안 |
| `accepted`, `completed` | 수용·완료 여부 |
| `started_at`, `ended_at` | 실험기간 |
| `cnt_lift`, `amt_lift` | 비교집단 대비 증분 |
| `margin_lift` | 원가·할인 차감 후 이익 변화 |
| `repeat_lift` | 재방문 변화 |

초기 서비스는 위험 프로필의 코사인 유사도를 이용한 `case-based retrieval`이다. 상호작용 로그가 업종·개선안별로 충분히 쌓이면 다음 점수를 결합한다.

```text
추천점수
= 유사 사업자의 개선안 성과
+ 현재 상권 위험 적합도
+ 트렌드 최근성
- 실행비용·실패위험
```

CF 적용 전에는 이를 Collaborative Filtering이라고 표현하지 않는다.

## 13. API

### `GET /health`

- 서비스 상태

### `POST /diagnose-region`

입력 예시는 다음과 같다.

```json
{
  "sido": "서울특별시",
  "sigungu": "강남구",
```

- 발표용 노트북 분석 코드 셀 60개 전체 실행, 오류 0건
- OpenAI·Neo4j 비밀정보 미포함 확인

실제 Neo4j 서버 적재와 실제 LLM 호출은 접속정보가 없으므로 수행하지 않았다. 코드에는 접속정보가 제공되면 실행되는 적재·호출 경로가 구현되어 있다.

## 17. 다음 단계

1. 주최 측에 동일 정의의 과거 BC 데이터 18~24개월을 요청한다.
2. 월별 rolling-origin backtest로 계절성과 지역 일반화를 평가한다.
3. 임계값 0.5를 고정하지 않고 학습기간 안에서 라벨별로 조정한다.
4. 확률 보정과 SHAP·계수 설명을 추가한다.
5. Neo4j 인스턴스에 실제 데이터를 적재하고 검색 쿼리를 검증한다.
6. LLM 답변의 근거 일치·과장·질문 유용성을 사람 평가한다.
7. 서비스 단계에서 사업자×개선안×성과 로그를 수집한다.
8. 충분한 상호작용이 쌓인 뒤 CF 또는 graph recommendation 모델을 학습한다.

최종적으로 발표에서 사용할 수 있는 표현은 다음과 같다.

> BC 소비와 외부 상권정보로 지역×업종의 복합 위험을 먼저 진단하고, Neo4j GraphRAG가 과거 상권 흐름과 실제 트렌드 사례를 검색한다. 이후 사업자 답변을 결합해 실행 가능한 개선 실험을 제안하고, 장기적으로 실제 개선성과를 학습하는 추천시스템으로 발전시킨다.
