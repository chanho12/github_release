# Codex 실행 프롬프트: 「같은 매출 변화, 다른 처방」 진단 구현·비교검증

## 0. 역할과 이번 작업의 목표

너는 이 프로젝트의 데이터 분석·진단 시스템 개발·평가 담당자다.
계획만 설명하지 말고, 아래 순서대로 실제 파일·코드·시험 결과를 작성하라.

고정할 주제:
「같은 매출 변화, 다른 처방」
BC카드 소비구조 분해 기반 상권 문제진단 및 맞춤형 개선안 제안.

이번에 검증할 질문:
“동일한 데이터를 제공했을 때, 소비구조를 체계적으로 분해하고 필요한 정보를
확인하는 절차가 일반 지표표·체크리스트 또는 일반 LLM 상담보다
근거에 맞는 점검 항목과 조건부 개선 후보를 제시하는가?”

현재 방어 가능한 범위는 지역·업종 수준의 점검 지원이다.
개별 점포의 원인 확정, 폐업예측 성공, 매출 개선, 처방 효과는 입증되지 않았다.
‘다른 처방’은 서로 다른 행동을 반드시 지시한다는 뜻이 아니라,
필요한 확인자료·점검 우선순위·조건부 실험이 달라질 수 있다는 뜻이다.
같은 점검이 적절한 사례에서는 같은 결론을 내도 정상이다.

이번에는 새 주제 탐색, H1~H18 전체 확장, 새로운 대규모 외부수집을 하지 않는다.
기존 자료 확정 → 진단 규칙 구현 → 평가사례 분리 → 공정한 비교 → 보고서 순으로 진행한다.

## 1. 프로젝트 상태 확인 및 실행계획 저장

먼저 작업공간에서 다음 자료가 실제로 있는지 조사하라.
- 최신 「같은 매출 변화, 다른 처방」 데이터 감사·재분석 보고서.
- 기존 분석 코드와 실행 로그.
- BC 원자료, 지역×업종×월 패널, 기존 외부 원본·가공자료.
- claim_reproduction.csv, external_data_decisions.csv,
  region_total_vs_industry.csv, case_pair_details.csv, case_pair_monthly.csv,
  evidence_cards.md 등 기존 산출물.

보고서에 파일명이 있다는 이유만으로 파일이 있다고 가정하지 않는다.
원자료가 없으면 보고서 수치를 복사해 ‘재현 완료’로 표시하지 않는다.
기존 코드를 재사용하고, 기존 결과를 덮어쓰지 않는 별도 실행 디렉터리를 만든다.

project_scope.md, execution_plan.md, artifact_manifest.csv를 작성한다.
manifest에는 실제 경로, 파일 역할, 해시, 연결된 코드·산출물, 확보 상태를 기록한다.
상태는 다음을 구분한다.
PLANNED / EXECUTED / FAILED / BLOCKED_MISSING_DATA /
BLOCKED_ACCESS / NOT_RUN_API / AWAITING_HUMAN_EVAL.

독립적으로 실행 가능한 작업은 계속하고, 막힌 작업은 이유와 필요한 입력을 기록한다.
승인 없이 유료 API 호출, 외부 업로드, 점주 연락을 실행하지 않는다.

## 2. 기존 주장 수정 및 데이터 버전 고정

### 2.1 최신 보고서의 참고값

아래는 새 분석 결과가 아니라 ‘이전 보고서에서 확인해야 할 주장’이다.
- BC 242,574행, 255개 시군구쌍, 11개 업종, 6개월.
- 완전관측 지역×업종 조합 2,327개.
- 원단위 OLS 성장착시 10개, 로그 OLS 성장착시 9개.
- 지역총량·개별업종 방향 불일치 679/2,327개.
- 그중 지역총량 상승·개별업종 감소 조합 432개.
- 같은 매출 변화의 설명용 비교 사례 4쌍.
- B0E와의 사람 비교평가 및 실제 개선효과 평가는 미실시.

기존 재현 로그를 확인하고, 실제 자료로 확인 가능한 핵심 수치만 재계산한다.
이전 실행이 검증돼 있다면 불필요하게 모든 과거 분석을 반복하지 않는다.

### 2.2 반드시 수정·확인할 주장

1. 679개에는 상승↔정체·감소↔정체도 포함된다.
   ‘모두 정반대 방향’ 또는 ‘기존 서비스 오류율’이라고 표현하지 않는다.
2. 432개를 제시할 때 전체 2,327개 대비 비중과,
   지역총량 상승 조합 2,027개 대비 비중을 구분해 재계산한다.
   어느 것도 ‘지역 수’의 비율이 아니다.
3. 기존 사례는 가능한 쌍 중 구조 차이가 큰 쌍을 선정한 것이다.
   재현 가능한 선정이더라도 대표성이나 효과 검증을 보장하지 않는다.
4. Pair 2·Pair 4는 첫 점검이 같은 것으로 보고되어 있다.
   4쌍 각각의 첫 점검 차이 / 추가 질문 차이 / 순서 차이를 따로 검토한다.
   ‘4/4 성공’은 사용하지 않는다.
5. 원래 성장착시와 다른 플래그를 합쳐 성장착시 발생률을 늘리지 않는다.
6. 동일 6개월에 OLS·Theil–Sen·전후반 비교가 일치한 것은
   강건성 검사이지 독립적인 검증이 아니다.
7. within/mix 63.7%·36.3%는 지역별 절대기여 비중의 중앙값이다.
   전국 총액의 기여율로 바꾸어 쓰지 않는다.

claim_corrections.csv에 기존 주장, 확인 근거, 수정 표현, 상태를 기록한다.

### 2.3 공통 정의

- CNT = 결제건수. 고유고객수·방문자수·재방문수가 아니다.
- AMT/CNT = 건당 평균 결제금액. 실제 상품가격·객단가·이익과 구분한다.
- 지역총량 = 제공된 업종 범위의 BC 이용금액 합계. 전체 지역경제가 아니다.
- 분석기간 = 2026년 1~6월. 시제품에서 현재 시점 실시간 데이터처럼 표시하지 않는다.
- 지역 식별은 시도와 시군구를 함께 사용한다.
- 로그 기울기는 β_AMT = β_CNT + β_건단가 관계를 검증한다.
  exp(β)-1로 변환한 성장률을 그대로 더해 항등식이라고 하지 않는다.
- ±0.25%/월은 기존의 실무적 중립구간이다. 통계적 유의성 기준이 아니다.
  주분석 설정을 고정하고 사전 지정한 0·0.5%/월 민감도도 별도로 확인한다.
  평가결과가 좋아지도록 임계값을 바꾸지 않는다.
- 결측은 임의로 0으로 채우지 않는다. 누락 구간·모집단 변경을 표시한다.

연령 분석은 숫자 연령 전체와 코드북상 국내 개인 범위를 구분해 민감도를 확인한다.
외국인이 숫자 연령에 포함되는 코드 충돌, 연령코드 1·2의 불명확한 구간을 기록한다.
확인하지 못한 연령구간을 추정해서 확정하지 않는다.
국내 개인도 해당 지역 주민과 동일 집단이라고 간주하지 않는다.

## 3. 기존 외부데이터의 사용범위 확정

기존 감사 판정을 재확인하되 다음 범위를 기준으로 삼는다.

- 주민등록 연령별 인구: CONTROL. 결제자와 주민의 모집단 차이를 표시.
- CPI: CONTROL. 전국 품목지수와 업종 매핑의 근사성을 표시.
- LOCALDATA 중국음식·제과점: MODULE_ONLY. 인허가 이력 기반 공급 점검.
- LOCALDATA 한식·일식·서양식·스넥: 제한적 민감도·사례 사용.
- 국세청 편의점·슈퍼마켓 가동사업자: MODULE_ONLY. 물리점포와 구분.
- 생활인구: 89개 인구감소지역, 2026년 1~3월에 한정한 MODULE_ONLY.
- 임대료·공실: CASE_ONLY. 시도·대표상권 값을 시군구 전체에 귀속하지 않음.
- 미확보 SEMAS 과거자료·관광 방문자 자료: HOLD.
- 시설좌표 KNN·대부분 마스킹된 국세청 폐업값: 이번 핵심 분석에서 제외.

HIGH 매핑은 업종 대응의 신뢰도이지 BC 가맹점과 동일 모집단이라는 뜻이 아니다.
AMT/외부 사업자수를 개별 가게 평균매출로 해석하지 않는다.
현재 스냅샷으로 과거 월별 공급을 만들지 않는다.
재구성된 인허가 패널은 재개업·이전·휴업·복수 인허가 등의 미확인 범위를 남긴다.
회계식 일치만으로 역사적 영업상태가 완전히 검증됐다고 하지 않는다.

외부자료를 모두 inner join해 핵심 표본을 축소하지 않는다.
모듈별 행·지역·업종·BC 금액/건수 포괄률과 가용기간을 기록한다.
공급이나 생활인구 자료가 없더라도 BC 핵심 진단은 실행하고 해당 모듈만 유보한다.

## 4. 진단 규칙과 Evidence Card 구현

LLM이 계산이나 원인 추정을 임의로 수행하지 않도록
지역·업종별 구조화된 근거카드를 먼저 생성한다.

Evidence Card 필드:
case_id, region, industry, period, source_ids,
monthly_AMT, monthly_CNT, monthly_ticket,
log_slopes, growth_rates, directions, robustness,
national_same_industry_comparison, region_total_vs_industry,
age_and_industry_composition, applicable_external_modules,
coverage, mapping_confidence, missing_information, limitations.

모든 숫자에는 단위·기간·계산법·분모·원자료 추적정보를 붙인다.
원자료의 빈칸이나 보고서의 결론을 관측값으로 만들지 않는다.

진단 규칙은 다음 ‘관찰 → 확인할 내용 → 금지할 단정’ 구조로 작성한다.

A. 결제건수 감소
→ 영업일·실제 점포 주문건수·확보 가능한 고유고객수를 확인.
→ 지역 CNT 감소만으로 고객 이탈·재방문 감소를 확정하지 않음.

B. 건당 결제금액 감소
→ 가격·할인·상품 및 주문구성·결제방식 변경을 확인.
→ 곧바로 가격인상·할인을 제안하지 않음.

C. 지역총량과 해당 업종 방향 불일치
→ 해당 업종의 건수·건단가·구성 및 전국 동일업종 흐름을 먼저 확인.
→ 지역 성장만으로 해당 업종이나 점포도 성장한다고 하지 않음.

D. 연령·업종 집중도 변화
→ 절대 건수와 비중을 함께 보고, 점포 고객·상품과의 관련성을 질문.
→ 고령층 증가·다양성 감소 자체를 위험으로 낙인찍지 않음.

E. 외부 공급 증가와 BC 소비 부진
→ 매핑·시점·모집단·실제 주변 경쟁 변화를 확인.
→ 과잉경쟁 확정 또는 실제 점포당 매출 하락이라고 하지 않음.

F. 특정 월 제거 시 추세 방향 변화
→ 월별 경로와 관측범위 변경·영업일·행사 가능성을 확인.
→ 한 달 민감도를 장기 쇠퇴나 피크 원인으로 단정하지 않음.

diagnosis_rules.csv 또는 YAML에 다음을 저장한다.
rule_id, trigger, required_fields, applicability_gate,
observed_fact_template, candidate_explanations, priority_rationale,
followup_question, answer_branch, conditional_action,
validation_metric, abstention_condition, prohibited_claims.

우선순위 규칙을 설명 가능하게 정하고 개발표본에서만 조정한다.
복수 설명이 가능하면 대안을 남기며, 자료가 없으면 원인을 미확인으로 표시한다.
질문은 이미 제공된 정보를 반복하지 않고, 다음 점검을 바꿀 수 있는 항목부터 묻는다.
이를 수학적으로 최적인 질문 선택이라고 주장하지 않는다.

개선 후보에는 반드시 적용 조건·필요한 점포자료·작은 시험 방법·확인 지표를 붙인다.
연락처·계좌·고객 식별정보 등 불필요한 개인정보를 요구하지 않는다.

## 5. 개발 사례와 평가 사례 분리

기존 4쌍은 설명·개발용으로 사용한다.
이 사례들에서 잘 작동하도록 수정한 규칙을 같은 사례로 평가하지 않는다.

예비평가 목표는 실제 지역×업종 20~30개 사례다.
이는 파일럿 목표이며 통계적 일반화를 보장하는 표본수는 아니다.

규칙·모델 선택 전 시군구 단위로 개발/평가 그룹을 고정하고 다음을 기록한다.
- 난수 seed와 추출 코드.
- 상승·정체·감소, 자료 충분·부족, 관측 규모 등 층화 기준.
- 해당 집단의 원래 빈도와 추출 확률.
- 개발 사례에 포함된 지역의 평가 제외 여부.

평가에는 구조가 다른 사례뿐 아니라 비슷한 사례·애매한 사례·자료부족 사례도 포함한다.
평가사례를 보고 임계값·규칙·프롬프트를 재선택하지 않는다.
불가피하게 수정하면 새 버전과 새 미사용 평가세트를 만든다.

현재 전체 데이터를 이미 EDA에 사용했으므로 완전히 새로운 외부 표본은 아니다.
‘규칙 개발과 분리한 내부 평가’라고 명시한다.
층화된 평가세트의 비율을 전국 발생률처럼 보고하지 않는다.

## 6. 공정한 비교 방식 구현

기존 보고서의 B0/B1/B2/B0E 명칭과 이번 실험명을 혼동하지 않도록 대응표를 만든다.
이번 비교는 다음 세 방식으로 한다.

A. 일반 지표표 + 일반 체크리스트
- AMT·CNT·건당 결제금액·연령·업종·사용 가능한 외부지표를 제공.
- 합리적인 일반 체크리스트를 제공하되 일부러 부실하게 만들지 않는다.
- 사람의 판단시간·정확도는 실제 사용자 수행이 있어야 측정한다.

B. 일반 LLM 상담
- 같은 사실자료와 점주 정보를 제공.
- 필요한 점검과 조건부 개선 후보를 요청.
- 정확성·불확실성·근거 표시라는 기본 지침도 동일하게 제공.

C. 우리 진단 절차 + 동일 LLM
- 같은 사실자료에 소비구조 분해 해석, 규칙, 질문 분기 절차를 적용.
- 사실·가능한 설명·미확인·다음 행동을 구분.

1차 비교에서는 원자료뿐 아니라 사전 계산된 관련 지표와 품질정보도
모든 방식에서 접근 가능하게 한다. C에만 중요한 숫자를 숨겨서 제공하지 않는다.
차이는 진단의 조직화·우선순위·질문 절차다.
분해 지표의 제공 자체를 평가하려면 별도의 사전 지정 ablation으로 분리한다.

B와 C의 모델·설정·출력예산·질문 가능 횟수를 맞춘다.
프롬프트·모델 식별자·파라미터·호출 시각·비용·지연·오류를 기록한다.
A도 비교 가능한 출력 공간을 갖게 하고, 분량 차이가 평가를 지배하지 않게 한다.

가능하면 C0 = ‘우리 규칙과 템플릿, LLM 없음’을 추가한다.
C0 대비 C가 나아지지 않으면 LLM 필요성이 입증되지 않은 것으로 보고한다.
이 비교가 없으면 규칙의 효과와 LLM의 효과를 완전히 분리했다고 하지 않는다.

LLM 실행 권한·키·예산이 없으면 프롬프트와 실행기를 작성하되 NOT_RUN_API로 남긴다.
템플릿 출력이나 임의로 작성한 예시를 실제 모델 응답으로 기록하지 않는다.

## 7. 추가 질문과 점포정보를 공정하게 처리

평가는 정적 설명과 추가 질문 후 판단을 구분한다.
1단계: 동일 Evidence Card에서 최초 점검과 필요한 질문을 출력.
2단계: 동일한 점포정보 조건에서 질문에 따라 설명·순서를 갱신.

실제 동의받은 익명 점포정보가 없으면 다음 원칙을 적용한다.
- BC의 실제 지역 사례와 가상의 점포 시나리오를 명확하게 구분.
- 가상점포는 시스템 분기 검증용이며 실제 점포에 대한 발견이 아님.
- 가상 가격·매출·고객정보를 실제 분석 패널에 합치지 않음.
- 실제 데이터/점주 제공/가상 시나리오/미확인 출처를 필드마다 표시.
- B와 C에 동일한 초기정보·질문예산·답변저장소를 사용.
- 준비된 정보가 없으면 ‘모름’으로 답하며, 시스템에 유리한 답을 생성하지 않음.
- 특정 지역의 실제 폐업·마케팅 실패 원인을 합성해서 정답으로 만들지 않음.

우리 규칙을 그대로 복사한 정답표로 우리 규칙을 평가하지 않는다.
실제 원인이 없는 사례는 원인 정답률이 아니라,
근거 범위 준수·필요한 확인사항·합리적인 점검과 유보를 평가한다.

산출물:
scenario_registry.csv, conversation_protocol.md,
각 방식의 원본 출력과 대화 로그, execution_status.json.

## 8. 자동 검증과 사람 평가를 분리

### 자동으로 실행할 항목
- 계산 항등식, 단위, 기간, 방향, 분모, 원자료 추적정보의 정합성.
- 결측·매핑 불가·과거자료 미확보 시 모듈이 작동하지 않는지.
- 동일 입력 반복 재현성과 질문분기 테스트.
- 개인정보나 API 키가 로그에 기록되지 않는지.
- 숫자·방향·출처처럼 기계적으로 확인 가능한 주장 일치율.

원인 단정·개선 적합성의 자동 탐지는 검토 후보로만 사용한다.
단순 키워드 검사나 또 다른 LLM 판정을 전문가 판단으로 간주하지 않는다.
‘테스트 PASS’가 ‘의사결정 개선효과 검증’과 같다고 하지 않는다.

### 사람 평가 준비

evaluation_rubric.md, blind_review_packets, human_ratings_template.csv를 만든다.
기본 항목:
1. 근거 일치성.
2. 필요한 점검 항목의 적절성.
3. 우선순위의 타당성.
4. 근거 없는 원인·점포 특성 단정.
5. 불확실성과 적용범위 설명.
6. 조건부 개선 후보의 적합성·실행가능성.
7. 점주의 이해도와 실제 수행시간·질문 부담.

전문가에게는 진단·점검 적절성을, 점주에게는 이해도·현실성·부담을 평가하도록 구분한다.
평가자는 가능하면 2명 이상, 방식명은 숨기고 제시 순서는 무작위화한다.
우리 방법만의 표현을 정답으로 보지 않고 복수의 합리적 점검순서를 허용한다.
최종 기준은 평가자가 테스트 출력물을 보기 전에 검토·고정하도록 한다.

사람 평가는 Codex가 대신 수행한 척하지 않는다.
실제 평가자가 없으면 템플릿·집계 코드까지만 작성하고 AWAITING_HUMAN_EVAL로 둔다.
가상의 점주 후기·만족도·전문가 점수·사용시간을 생성하지 않는다.

평가자료가 실제 들어오면 같은 사례 단위의 paired 비교를 한다.
효과크기·불확실성·평가자 불일치를 보고하고,
같은 사례의 반복 출력이나 여러 평가자를 독립 지역표본으로 세지 않는다.
소표본은 기술통계를 우선하며, 미실시 항목은 0점이 아니라 미측정으로 남긴다.

## 9. 최소 시제품

기존 기술스택을 우선 사용한다. 우선순위는 웹 UI보다 재현 가능한 진단 함수와 CLI다.

한 가지 흐름만 구현한다.
지역·업종 선택 → 분석기간·관측범위 확인 → 근거카드 → 추가 질문
→ 우선 점검 항목 → 조건부 개선 후보.

출력 형식:
- 확인된 지역·업종 사실.
- 적용 가능한 해석과 대안 설명.
- 아직 모르는 점포정보.
- 다음 확인 항목과 그 이유.
- 조건이 충족되면 검토할 개선 후보.
- 작은 시험 방법·확인 지표·재검토 조건.
- 데이터 기간·외부자료 한계·근거 ID.

점포 정보가 없으면 지역 진단 모드로 작동하며, 개인화가 완료됐다고 하지 않는다.
LLM이 없으면 규칙·템플릿 모드임을 화면과 로그에 명시한다.
분석결과에 없는 성공률·폐업확률·예상 매출증가율을 출력하지 않는다.

## 11. 실행 우선순위와 완료 보고

1~3을 먼저 실행해 자료와 주장을 고정한다.
그다음 평가 분리 규칙을 고정하고 4~5의 진단·사례 작업을 진행한다.
6~8의 비교 실행기·자동검증·사람 평가 패키지를 만든다.
9~10의 최소 시제품과 보고서를 작성한다.
새 데이터 확보나 사람 평가가 막혀도 수행 가능한 구현과 테스트는 계속한다.

마지막 답변은 다음 여섯 항목으로 요약한다.
① 실제 완료한 작업과 저장 경로.
② 재현·수정·미확인된 주요 주장.
③ 일반 지표표 대비 새로 정리할 수 있었던 점검 내용.
④ 같은 조건에서 비교했을 때 개선이 입증된 부분과 미입증 부분.
⑤ 사람에게 필요한 입력·평가·권한.
⑥ 다음 실행 명령과 남은 Todo.

가장 중요한 기준:
“선정한 사례에 다른 설명을 붙였는가?”가 아니라,
“같은 자료에서 더 적절하고 근거에 맞는 점검을 돕는가?”를 검증하라.
차이가 없거나 규칙 기반 방식으로 충분하다면 그 결과도 그대로 보고하라.
